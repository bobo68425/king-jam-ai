# 募資行銷活動模組設計

## 一、業務概述

透過外部募資網站（如 flyingV、嘖嘖）增加訂戶：用戶在募資網站選定專案方案並付款後，我們產生一組**銷售碼**，用戶可在 King Jam AI 訂閱頁面輸入該**結帳碼（優惠碼）**完成兌換，直接開通對應訂閱方案。

### 專案類型

| 專案 | 說明 | 對應訂閱方案 |
|------|------|-------------|
| 部落客專案 | 適合部落格寫作者 | 入門版 |
| 自媒體專案 | 適合社群、影音創作者 | 專業版 |
| 超級小編專案 | 適合一人多工小編 | 專業版 |
| 新創老闆專案 | 適合新創團隊 | 企業版 |

### 方案層級

每個專案有兩檔：
- **超早鳥**：較早贊助，價格最優
- **早鳥**：較晚贊助，價格次優

## 二、資料模型

### 2.1 募資專案 (funding_projects)

| 欄位 | 類型 | 說明 |
|------|------|------|
| id | int | PK |
| project_code | varchar(50) | 專案代碼（blogger, self_media, super_editor, startup_boss） |
| name | varchar(100) | 顯示名稱 |
| description | text | 說明 |
| target_plan_code | varchar(50) | 對應訂閱方案（basic, pro, enterprise） |
| subscription_months | int | 訂閱月數（例：6、12） |
| fundraising_platform | varchar(50) | 募資平台（flyingv, zeczec, other） |
| platform_url | varchar(255) | 募資頁面連結 |
| is_active | bool | 是否啟用 |
| sort_order | int | 排序 |
| created_at, updated_at | datetime | 時間戳 |

### 2.2 募資方案層級 (funding_tiers)

| 欄位 | 類型 | 說明 |
|------|------|------|
| id | int | PK |
| project_id | int | FK → funding_projects |
| tier_code | varchar(50) | 層級代碼（super_early_bird, early_bird） |
| tier_name | varchar(100) | 顯示名稱（超早鳥、早鳥） |
| fundraising_price_twd | decimal | 募資平台售價（NT$） |
| original_price_twd | decimal | 原價（用於顯示折扣） |
| is_active | bool | 是否啟用 |
| sort_order | int | 排序 |
| created_at, updated_at | datetime | 時間戳 |

### 2.3 銷售碼 (sales_codes)

| 欄位 | 類型 | 說明 |
|------|------|------|
| id | int | PK |
| code | varchar(32) | 銷售碼（唯一，可讀格式如 KJ-BLOG-SEB-XXXX） |
| tier_id | int | FK → funding_tiers |
| status | varchar(20) | pending(未使用), redeemed(已兌換), expired(已過期) |
| redeemer_user_id | int | FK → users，兌換者 |
| redeemed_at | datetime | 兌換時間 |
| order_id | int | FK → orders，關聯訂單 |
| expires_at | datetime | 過期時間 |
| external_order_id | varchar(100) | 募資平台訂單編號（可選） |
| notes | text | 備註 |
| created_at, updated_at | datetime | 時間戳 |

## 三、流程設計

### 3.1 銷售碼產生流程

1. **預先生成**：管理員在後台依募資方案批次產生銷售碼
2. **單筆產生**：確認募資平台付款後，手動或 API 產生一組碼
3. **發送**：透過 Email / 募資平台後台 / 人工發送給贊助者

### 3.2 用戶兌換流程

```
用戶登入 → 訂閱頁面 → 輸入結帳碼 → 驗證 → 顯示可兌換方案 → 確認兌換 → 0 元完成 → 開通訂閱
```

- 兌換時建立 **0 元訂單**，`payment_provider` 為 `sales_code`
- 訂單狀態直接設為 `completed`，履行訂閱開通

### 3.3 API 設計

| 方法 | 路徑 | 說明 |
|------|------|------|
| GET | /payment/sales-code/validate?code=XXX | 驗證銷售碼（未登入可驗證） |
| POST | /payment/sales-code/redeem | 兌換銷售碼（需登入） |
| GET | /admin/funding/projects | 管理員：募資專案列表 |
| POST | /admin/funding/projects | 管理員：建立專案 |
| GET | /admin/funding/tiers | 管理員：方案層級列表 |
| POST | /admin/funding/tiers | 管理員：建立方案 |
| POST | /admin/funding/sales-codes/generate | 管理員：批次產生銷售碼 |
| GET | /admin/funding/sales-codes | 管理員：銷售碼列表 |

## 五、前端 UI

### 5.1 訂閱頁面

- 新增「我有募資結帳碼」區塊
- 輸入框 + 驗證按鈕
- 驗證成功後顯示可兌換方案，點擊「確認兌換」完成

### 5.2 管理後台

- 募資專案管理：CRUD 專案、方案層級
- 銷售碼管理：批次產生、匯出、查詢使用狀態
